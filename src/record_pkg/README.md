# HRM recorder

**Numeric data from 3D estimation, four motors, and four load cells are saved as
original ROS messages and CSVs.** **Cropped HRM color images and numeric depth
from the same ROI are saved as separate image files.**
The GUI service `/data/record` is unchanged. **Starting the Record component and
starting a recording are separate actions.** The recorder never publishes motor
commands or changes the physical output enable state.

## Control-experiment CSV (2026-10-26)

After Record Stop, the existing export process also creates
**`csv/control_tracking.csv`** and `csv/control_tracking.schema.json`.
The 268-column training `summary.csv` and existing per-topic CSVs are unchanged.
This follows the existing post-recording conversion of numeric bags, rather than
writing the CSV in real time during recording.

| Category | Main columns / meaning |
|---|---|
| Control reference | `control_mode`, `source_time_ns`, `feedback_time_ns`, `elapsed_s`, `contact_segment_id` |
| Kinematics command | `pan_rad`, `tilt_rad`: signed radians actually passed to cable IK, not tip Euler orientation |
| Position/Admittance command | `nominal_y_m/z_m`: original target; `target_y_m/z_m`: target used in that position-control step, after displacement correction in Admittance mode |
| Curve-derived tip | `estimated_tip.x_m/y_m/z_m`: final, length-corrected boundary point |
| Joint-angle FK tip | `fk_tip.x_m/y_m/z_m`, `fk_tip_tf.x_m/y_m/z_m/qx/qy/qz/qw/roll_deg/pitch_deg/yaw_deg` |
| Estimated tip orientation | `estimated_tip_orientation.qx/qy/qz/qw/roll_deg/pitch_deg/yaw_deg`: final-link DH orientation; the **position of `center_19` is not used as the tip** |
| Position error | `target_minus_fk_y_m/z_m/yz_norm_m`: applied target minus FK position derived from observed angles |
| Matching status | Each group's `source_time_ns`, `bag_receive_time_ns`, `time_difference_ms`, `matched`, `numeric_valid`, `frame_id` |

Positions are in meters in `hrm_base`, pan/tilt commands in radians, and displayed
Euler angles in degrees. X is observed and recorded only; no control axis is added.
Kinematics has no Cartesian target, so nominal/target XYZ and position-error
columns are blank. Position/Admittance pan/tilt columns contain the angle commands
generated by the position controller, not position targets.

- Each new `/control/reference` message produces one row. The message records
  command-generation time, mode, command values, and feedback-image time, so the
  mode is not inferred from the old headerless `/surgical_tool_pose`.
- Every sinusoidal command update is recorded. A one-shot fixed Kinematics command
  is recorded only when issued; it is not periodically republished while the
  target is held. For fixed-command experiments, **send the command after starting
  Record**. Commands sent only before recording are neither reconstructed by
  inference nor automatically repeated across subsequent tip frames.
- Tip data are matched nearest to command time for Kinematics and to the image
  time used by the calculation for Position/Admittance. Both times are preserved
  separately. Position and orientation streams are matched independently, so
  identical capture times are not guaranteed.
- As with existing tip storage, matching is **nearest with no time-difference
  limit**. This bridges temporary gaps but can also attach old or future samples
  across long gaps. `time_difference_ms` is tip time minus reference time; no
  delay compensation or interpolation is applied. Inspect timing and validity
  columns before calculating RMSE. Truly missing data or frames other than
  `hrm_base` remain blank, not zero-filled.
- `motor_output_enabled` reports the configured output gate, not confirmation
  that a motor command physically succeeded. Other protection conditions may
  block output. Neither the recorder nor CSV export moves motors or changes
  control logic, gains, or safety conditions.
- `/control/reference`, `/position/sine_reference`, and `/position/sine_status`
  are included in the default recording list but are **not mandatory startup
  requirements**. This separate CSV does not depend on sensor/training-summary
  readiness. Set `control_tracking_csv.enabled=false` to disable only this CSV.
- Older bags/controllers without the new topic produce a header-only CSV and
  `no_commands` status. Existing topic data and summary remain unchanged;
  existing datasets are not automatically re-exported or overwritten.

To apply the update, finish recording/export and motor motion, safely stop the
relevant nodes, then run:

```bash
source /opt/ros/humble/setup.bash
colcon build --symlink-install --packages-select custom_interfaces robot_control_pkg record_pkg
source install/setup.bash
```

Restart the controller and Data recorder to use the new message/recording list.
If per-topic CSVs already contain `/control/reference` but the additional CSV is
missing:

```bash
ros2 run record_pkg export_control_tracking /absolute/session/csv
```

This command refuses to overwrite either existing output file. Detailed column
definitions and missing/matched counts are in `control_tracking.schema.json`;
automatic export results are in `manifest.json` and session `postprocess.json`.

Validation for this update passed: isolated builds of the three packages, 490
recorder functional tests, an actual offline bag-to-CSV round trip with the new
message, and Kinematics/Position/Admittance dry-run publication checks in DDS
domain 84. Motor output was false and no actuator messages were published.
Existing C++ functional tests passed; package-wide lint still had pre-existing
style errors. Running controller/recorder nodes were not restarted.

## Optional image recording (2026-09-27)

Select **Save crop RGB/depth** in the GUI Recording settings for each session.
The default checked state preserves crop color/depth recording. When unchecked,
neither image archive is created; numeric bag, CSVs, `summary.csv`, and metadata
are still saved. Small metadata such as CameraInfo/depth calibration may remain.
With image saving off, missing image sources do not block recording through image
requirements or postprocessing errors. Live camera/estimator/GUI operation is
unaffected, but those sessions cannot support image reprocessing.

- The boolean `save_images` parameter on `/record` defaults to true. The GUI
  sets it atomically with force alignment and contact ID, and requests Record
  only after a successful response.
- Changes are rejected during recording, shutdown, image flushing, or CSV export.
  Select the setting before the next Record.
- Applied settings are saved in `session.json` as `snapshot.save_images` and
  `snapshot.*_archive_settings`, and in session `recording_config.json`.
  Postprocessing reads these values and marks disabled archives as `disabled`.
  `/data/record_status.save_images` is also available.
- Re-enabling restores archive.enabled from the configuration read at node
  startup. Archives disabled in that configuration are not forcibly enabled.
  Numeric topic selection and CSV schemas do not change.
- This option controls crop file archives. The default bag contains no images,
  but custom profiles that add image bag topics must adjust those separately.
- Existing recording directories are unchanged. After the update, restart the
  GUI and Data recorder when recording/export has finished; do not restart nodes
  during recording.

## Lightweight image-storage profile

The default image sources are only `/estimated_segment_crop_image` and
`/estimated_segment_crop_depth/image_raw`.
Lossless PNGs are saved in `images/hrm_crop/`, **without duplicating the same
images in the bag**. Depth is saved under `images/hrm_crop_depth/` as 16-bit PNG
(16UC1/mono16) or float32 NPY (32FC1). Invalid depth values such as 0 and NaN are
preserved without colorization or normalization.
Full HRM color/depth, tag-camera video, body binary/skeleton images, and 3D
visualizations (point clouds/markers) are excluded from default recording.
Live GUI/RViz display and estimation/tag-detection calculations are unchanged.

- Existing `csv/summary.csv`, per-topic numeric CSVs, metadata, and numeric bags
  remain. **Bags have not been removed; large image payloads are excluded.**
- PNGs and `images/hrm_crop/index.csv` associate files with original source
  timestamps and frames. The index stores filename, receive time, dimensions,
  encoding, contact label, and capture time. The depth index also stores each
  frame's ROI, crop-relative K/P/R/D, original dimensions, and
  `depth_scale_m_per_unit`; `depth_m = raw * scale`.
- Image callbacks enqueue into a bounded queue; a separate worker compresses PNGs
  and writes files. Queue drops caused by overload and write errors are recorded
  in status/manifests. Lossless PNG means saved pixels are preserved, not that
  every camera frame is guaranteed to be received.
- **Crop images suffice to recompute 2D masks/skeletons**, but must not be cropped
  a second time as if they were original images. Use the recorded ROI/settings;
  pixels outside the crop cannot be recovered. Saved depth and calibration allow
  3D reprocessing within the ROI. RGB/depth keep independent source stamps and
  must be aligned within the session. Neither identical exposure times nor the
  exact online RGB/depth pairing is guaranteed. Tag images cannot be re-detected.
- Existing session bags/PNGs/CSVs are not deleted or modified. Default-profile
  changes apply **to new sessions after restarting the estimator and Data
  recorder**.

## Separate recordings when moving the sensor (2026-09-26)

The final user choice retains **Stop followed by a new Record**.
No pause/resume button or `interval_id` column is added. After Stop/export
completes, move the sensor and start a new Record to create a separate timestamped
session directory. Record Stop does not stop motors; stop any required motion
separately.

For LSTM/TCN training, construct continuous-frame windows within each file, then
combine the completed windows. Concatenating CSV rows before windowing introduces
artificial continuity across session gaps. Split train/validation by experiment
or session before building windows, and preserve order within each window.
Non-temporal models do not automatically ignore IDs or timestamps either:
training code must explicitly select input columns. Training code and dataset
splitting are not implemented by this recording change.

## Contact-experiment labels and additional relative angles (2026-09-25)

- GUI `contact_segment_id` accepts integers 0–18. Zero denotes a no-load
  free-motion experiment; 1–18 denote the user-selected contact segment.
- Set it before Record. Collection starts only after recorder approval; the value
  is fixed during collection, stopping, and CSV export. Change it after Stop and
  export complete. Applying/releasing force does not change the label; there is
  no force-threshold decision.
- The fixed value is stored at `session.json` → `snapshot.contact_segment_id`
  and in every row of per-topic time-series CSVs and `summary.csv`.
  Key/value `session_metadata.csv` stores it as a snapshot item.
  Older recordings without a label remain blank rather than being assumed zero.
- Angle-topic CSVs and summary add `relative_angle_1`–`relative_angle_18`.
  The fixed rule is odd joint = same-index `tilt_relative`, even joint =
  `pan_relative`. Values come from the same message, preserving radians, sign,
  and zero. No axis substitution, absolute value, summation, or recalculation
  of angles is performed.
- These 19 label/relative-angle columns are appended to summary. After the
  2026-09-25 selection, it has 268 columns; original relative/absolute pan/tilt
  values are preserved.
- Tilt-first was confirmed with the user and matches the estimator's odd-tilt,
  even-pan active axes. Estimation/FK calculations were not changed.
- Existing bags/CSVs are not overwritten. Training, one-hot/soft labels, and
  networks are outside this implementation.

## Running

```bash
source /opt/ros/humble/setup.bash
colcon build --symlink-install --packages-select estimation_pkg record_pkg gui_py_pkg
source install/setup.bash
ros2 launch record_pkg _launch.py
```

The GUI provides the same workflow: System → **Data recorder → Start**, then
**Record**. Recording does not begin automatically.

GUI states are `starting → recording → stopping → exporting → stopped`.
Do not start data-collection motion before `recording`; **wait for `stopped`
before closing the system or powering it off**. `exporting` means the bag is
closed and CSV/missing-data checks are underway; new Record requests are temporarily
blocked. Orange `INCOMPLETE` means finalization finished but required numeric data
or image recording had problems. The save path appears in the status tooltip and
node log. A dead node is shown as stale, and failed service requests are not
reported as successful.

Terminal control/checks:

```bash
ros2 service call /data/record std_srvs/srv/SetBool '{data: true}'
ros2 topic echo /data/record_status
# After motion/data collection has finished:
ros2 service call /data/record std_srvs/srv/SetBool '{data: false}'
# After the status becomes stopped, substitute the actual session directory:
ros2 bag info record/<session>/bag
```

The default output is **`record/` under the working directory used to launch the
process**. To use another disk:
`ros2 launch record_pkg _launch.py output_root:=/absolute/dataset/path`.
Each recording creates a new date/time/microsecond directory without overwriting
existing sessions. The format is `YYYYMMDD_HHMMSS_ffffff` (PC local time; final
six digits are microseconds), for example `record/20260915_200630_017213/`.
`session.json` stores the same `session_id` and UTC/local start times, including
the timezone offset.

## Recorded content and configuration

Select topics through `enabled_groups`, `extra_topics`, and `required_topics`
in [config/recording.json](config/recording.json).
Configuration is read at recorder startup, so **restart the recorder after
changing it**. Check the actual installed path to determine whether source and
installed configuration are symlinked. Another configuration can be supplied
with `config_file:=/absolute/recording.json`.

Topics **selected for recording** differ from topics **required to start**.
Removing a topic only from `required_topics` allows startup without it while
still saving incoming messages if it remains selected. To exclude it from the bag
entirely, also remove its group or its entry in `topic_groups`/`extra_topics`.
Required topics must be a subset of selected topics. For example, selecting only
the sensor group and requiring only `/fts_data` and `/loadcell_state` records
the other sensor-group topics only when published.
There are no GUI checkboxes for this list; edit the configuration and restart
Data recorder. PNG archives use separate settings below. Do not add crop images
to bag-only `required_topics`. With `required: true`, the default Record also
needs a crop publisher.

```json
"image_archive": {
  "enabled": true,
  "topic": "/estimated_segment_crop_image",
  "queue_size": 16,
  "required": true
}
```

Depth saving is controlled by `depth_archive`
`enabled/topic/metadata_topic/queue_size/required`.
Defaults are `enabled: true, required: false`, so older estimators without the new
depth topic do not block recording. **Missing depth is reported in status and
depth_integrity.** Verify saved depth counts before experiments requiring 3D
reprocessing. The crop depth publisher uses the same ROI and original header;
calibration is matched by exact depth stamp/frame. Missing or mismatched
calibration records errors instead of producing misleading 3D-reprocessing files.

| Group | Recorded content |
|---|---|
| camera | D405 color/aligned-depth and crop-depth CameraInfo, ROI/scale metadata; no image payloads in the bag |
| sensors | `/fts_data`, `/fts_data_kalman_filter`, both sensor offsets, four-channel `/loadcell_state`, `/data_filter_setting` |
| motor_and_control | Four-motor states/commands, actual cable displacement/velocity, `/kinematics/target_wire_length`, `/kinematics/fk_tip_position`, control mode, pose, position/admittance diagnostics, existing dynamics diagnostics, force estimates |
| geometry | New `SegmentAngle` (all pan/tilt and angular-velocity arrays), `/estimated_tip_position`, `/estimated_tip_position_unscaled`, `/tf`, `/tf_static` |
| apriltag (optional) | Tag-camera `color/camera_info`, `/detections`, and three `/apriltag/.../pose` topics; saved when published, with recording allowed even without detections or a running tag camera; no tag images |
| visualization (OFF by default) | Available as an option; enabling explicitly adds crop/body/skeleton images, centerline point clouds, and reconstruction markers to the bag |
| configuration | `/parameter_events` |

If camera calibration topics change, **update the camera/apriltag groups and
required_topics together**. Set a changed crop PNG topic in `image_archive.topic`.

The default required bag topics are color CameraInfo, motor_state, loadcell_state,
raw/Kalman F/T, wire_length, estimated_segment_angle, and tool_endeffector_pose.
Crop PNG readiness is checked separately through `image_archive.required`.
Startup is rejected if a publisher is absent or recent valid timestamps on small
required messages do not advance. **Tag-camera CameraInfo, detections, and all
three poses are optional**: recording may start/continue without them, and tag
absence alone does not trigger required-data `INCOMPLETE` warnings. Topic lists
and CSV columns remain; detections that do arrive are saved. If no matching tag
pose exists, its summary cells remain blank/unmatched. Empty `/detections`
arrays or unrelated `/tf` frames do not count as tag detections.
Output commands, mode changes, mode-specific diagnostics, and AI force estimates
are event- or mode-dependent, so they are optional rather than globally required
periodic topics.

The default bag contains no images; crop color/depth are subscribed separately
for file archives. Check each archive for topic selection, queue drops, and write
errors. Small numeric messages are monitored through auxiliary BEST_EFFORT
keep-last-1 subscriptions; this monitoring does not itself guarantee bag storage.
The default `required_max_gap_sec` of 2 seconds is a data-quality warning
threshold, not a controller protection timeout. Interruptions during collection
are reported as GUI `DATA WARNING` and in `live_health_events`, but **remaining
data collection continues and motors are not controlled**. Exceeding
`startup_timeout_sec` (default 10 seconds) stops only this recorder's capture.

After stopping, actual SQLite receive times are checked for zero-message required
topics and long intermediate/end gaps, reported in `postprocess.json` and
`session.json.data_quality`. The checked interval runs from recording-ready to
the first Stop request, avoiding false gaps during preparation/flushing.
`complete` means this reception-continuity check passed, not sensor accuracy,
source-clock synchronization, or lossless reception of every frame.
`allow_incomplete:=true` is only for development tests without sensors; missing
data remain missing. Tag-free experiments work with the default configuration.
Remove apriltag from `enabled_groups` only to exclude tag data from recording
entirely. If a custom configuration added tag `required_topics`, check those
requirements separately.

Numeric storage retains raw/Kalman force and existing dynamics diagnostics.
The `visualization` group remains available but defaults to disabled. Enable it
explicitly only when needed, since it adds large messages and duplicate crop
storage. Original 2D friction/dynamics-derived CSV calculations are retained in
[legacy/record_node_2d.py](legacy/record_node_2d.py).
The old AprilTag relative pose was ID1 relative to ID0; the current pose/CSV
restores this representation. It does not stamp cached latest values with image
times or save zero/previous tag values for missed detections.
**Existing experiment files have not been deleted or modified.**

### Unified summary.csv (selection updated 2026-09-25)

After Record Stop, **`csv/summary.csv`** is generated automatically alongside
the per-topic CSVs.

F/T torque `tx, ty, tz` from `/fts_data` and `/fts_data_kalman_filter` is
saved to one decimal place in both per-topic CSVs and summary. Precision of force,
motor torque, coordinates, angles, and other columns is unchanged; original
rosbags are preserved. Existing CSVs are not automatically overwritten.
Use this table as the **source for training inputs and data inspection**.
Selection of X/Y columns, handling of intermediate missing values, interpolation,
filtering, and train/evaluation splits belong in the separate training repository.
A successful CSV export alone does not mean the data are ready for training.

#### Start once essential training signals are available (2026-09-26)

The new default profile sets `summary_csv.startup_required_groups` to
`["motor", "loadcell", "fts", "wire", "angles"]`.
Summary begins at the first angle row whose matches pass the existing timing
rules and whose required values below are all finite.

- Four motor positions, four load-cell tensions, raw F/T force XYZ, four cable
  lengths, and 18 active-axis relative angles (odd tilt / even pan).
- If session force alignment is enabled, aligned force XYZ and transformation
  validity are also checked. Aligned columns are not required when it is disabled.
- Tags, tip/FK, motor acceleration/torque, cable velocity, and Kalman force are not
  default startup requirements. `fts_kalman`/`wire_velocity` can be required
  explicitly. Sensor-specific profiles should list only their required groups.
  `[]` retains the previous behavior of keeping the initial interval.
- Zero and negative values are valid numbers. Unmatched values, NaNs, and invalid
  arrays are not filled with another time's value, a previous value, or zero.
  The sensor matching tolerance remains ±25 ms.
- **Only the initial readiness interval is excluded.** Later incomplete rows are
  not deleted; blanks, matched flags, and actual time intervals remain.
  Original bag/per-topic CSV data and the 268-column schema are unchanged.
- Original timestamps and the `elapsed_s` origin are preserved, so the first
  exported elapsed_s may exceed zero. `summary.schema.json.startup` and the CSV
  manifest report excluded-row counts, per-group unmet counts, first output time,
  and unmet rows after startup.
- If readiness is never reached simultaneously, output is header-only with
  `no_common_start`; export reports `partial`. Originals are preserved, and
  the result is not presented as a valid training table. This differs from
  `no_angle_samples`, which means no angle samples existed.

Defaults apply to new sessions after restarting Data recorder. Older session
configuration copies without this option retain previous export behavior;
existing summary files are not automatically overwritten.
Manual `export_summary` reads the session configuration. Override explicitly
with `--startup-required-groups motor loadcell fts wire angles` if needed.
Use this only in a **new CSV export directory** without an existing summary.

Each row corresponds to one valid original timestamp from
`/estimated_segment_angle`. The current 268-column selection removes nine
unscaled-tip position/timing columns from the previous 331-column version and
replaces 72 angular-velocity columns with 18 active-axis relative velocities.
Only summary selection changes; original topic recording and per-topic CSVs remain.

| Category | Example columns / meaning |
|---|---|
| Four motors | `motor.Motor #1 position [count]` … `#4`; separate velocity, acceleration, and torque columns too |
| Four load cells | `loadcell.Loadcell #1 tension` … `#4`; separate voltage columns too |
| F/T | `fts.fx/fy/fz/tx/ty/tz`, `fts_kalman.*`; original units |
| Cables | `wire.Cable #1 length` … `#4`, `wire_velocity.*`; displacement/velocity converted from motor feedback |
| Joint angles | `pan_relative_01_rad` … `18`, `tilt_relative_*`, `pan_absolute_*`, `tilt_absolute_*` |
| Active-axis relative angles | `relative_angle_1` … `relative_angle_18`; tilt1, pan2, …, pan18 (rad) |
| Active-axis relative angular velocities | `relative_angular_velocity_1_rad_s` … `relative_angular_velocity_18_rad_s`; same tilt-pan order |
| Depth-fitted endpoint | `estimated_tip.x_m/y_m/z_m`; unscaled excluded only from summary |
| FK tip | `fk_tip.x_m/y_m/z_m` (PointStamped), `fk_tip_tf.*` (TF position + rotation) |
| Estimated final-link orientation | `estimated_tip_orientation.qx/qy/qz/qw`, `roll_deg/pitch_deg/yaw_deg` |
| Tags | `tag_id0_to_id1.x_m/y_m/z_m`, `qx/qy/qz/qw`, `roll_deg/pitch_deg/yaw_deg` |

**Each pan/tilt array retains 18 entries indexed by physical joint number.**
Relative angles use tilt on odd joints and pan on even joints; original inactive
axis zeros are preserved. This does not mean there are 36 rotational joints.
Absolute angles describe each segment's direction in hrm_base and are not simple
sums of relative angles; both absolute axes may contain nonzero values.
The 18 angular velocities select `tilt_angular_velocity_relative` for odd joints
and `pan_angular_velocity_relative` for even joints from the same angle message.
Zeros, signs, and rad/s are preserved without new differentiation/filtering.
All four original relative/absolute angular-velocity arrays remain in per-topic
CSVs and bags.

The command path is target tilt/pan → IK target cable lengths → motor command.
However, `wire.*` above is **converted actual motor position/velocity**, not
the IK target. `/kinematics/target_wire_length` remains separately recorded
in the bag and per-topic CSV.

Tag columns separate translation and rotation of `ID0_T_ID1`; the same data
are not duplicated as 16 homogeneous-matrix entries. Rotation is stored as the
original xyzw quaternion and derived extrinsic XYZ Euler angles (degrees),
i.e. `Rz(yaw) Ry(pitch) Rx(roll)`.
**Tag mounting translation/rotation compensation has not yet been applied.**
Future `base_T_ID0` and `ID1_T_tip` compensation should add derived columns
without overwriting the original tag columns.

`estimated_tip` is the fitted curve's final **boundary point**;
`fk_tip_tf` is the kinematic tip. `estimated_tip_orientation` uses only the
**rotation** of the final-link-center TF, not its center position as the tip.
This orientation comes from filtered DH angles, not an independent depth-based
roll observation. Interpret it accordingly when comparing with FK rotation
derived from the same angles.

#### Time matching and blank values

- Sensors and tags use the nearest original timestamp within ±25 ms by default.
  Past or future samples may be selected, and one sample may be reused across
  multiple rows. This is not a complete training synchronization procedure.
- `estimated_tip`, `fk_tip`, `fk_tip_tf`, and `estimated_tip_orientation`
  select the sample nearest to the angle-image timestamp **without a time limit**.
  Past and future samples are eligible; exact timestamps take priority and ties
  choose the past sample. Neither `max_time_difference_ms` nor its CLI option
  applies to these four groups. Distant samples may be reused across gaps or after
  publication stops, so inspect actual `time_difference_ms` during training.
  Time differences and original timestamps are not overwritten.
  Their schema entries record `matching=nearest_unbounded` and
  `max_time_difference_ms=null`. This policy applies from 2026-10-11;
  existing summaries are not changed automatically.
- Each group retains `matched`, `source_time_ns`, `bag_receive_time_ns`,
  `frame_id`, `time_basis`, and `time_difference_ms`.
  `matched` means only that a temporal match succeeded, not that sensor health,
  force calibration, or camera synchronization is guaranteed.
- Headerless cable topics are matched against the angle message's **receive time**
  and marked `time_basis=receive`; no source timestamp is invented.
- If a `/detections` CSV exists, the nearest detection frame must contain both
  ID0 and ID1, and only a relative pose with exactly that frame's timestamp is
  used. Explicit missed detections are not filled from nearby valid poses.
  Without detections, `detection_guard=unavailable`.
- Sensor/tag samples outside their time limit, unreceived values, invalid numbers,
  and incorrect array lengths remain blank. The four tip groups are not blanked
  merely for age. Actual zeros remain zero.
- After startup readiness, rows are not dropped just because some fields are
  blank. However, an angle anchor with a zero/missing, duplicate, or backward
  timestamp is excluded from summary, with counts recorded in the schema.
  Per-topic CSV/bag reception records remain untouched; unpublished/unreceived
  messages are not synthesized.
- Times are needed to inspect sample spacing and matching. Row order alone cannot
  reveal dropped frames or processing delays. Training must also preserve session
  boundaries between files.
- `matched=False` does not cause automatic exclusion from training. Distinguish
  finite noisy data from missing/mismatched ground truth; decide missing-value
  handling and training masks in the training repository. No additional
  quality-threshold filter was introduced here.
- With no angle samples, only a header is generated with `no_angle_samples`.
- Intermediate TFs, event-driven commands, settings, and diagnostics remain in
  selected bag/per-topic CSVs rather than being repeated in this summary.
  Crop PNGs are in `images/hrm_crop/` with `index.csv`; other images/clouds/
  markers are not recorded by default.

Matching policy and column definitions are saved in `summary.schema.json`.
Configuration:

```json
"summary_csv": {"enabled": true, "max_time_difference_ms": 25.0}
```

For a recording already exported to per-topic CSVs, add only the summary with
the following command. An existing summary is not overwritten.

```bash
ros2 run record_pkg export_summary /path/to/session/csv
```

### Estimated and FK endpoint CSVs (2026-09-21)

The following three topics use `geometry_msgs/PointStamped`, each saving
**XYZ in meters in `hrm_base`** and its original source stamp in an independent
CSV. They are optional and do not extend existing `required_topics`.
If essential to an experiment, explicitly add them to the required list and
restart Data recorder.

| Topic | Meaning |
|---|---|
| `/estimated_tip_position` | Final boundary point of the depth-based 3D fitted curve, after configured hardware-length correction; **not the last segment's center** |
| `/estimated_tip_position_unscaled` | Endpoint of the same fitted curve **before scaling to total hardware length**; fitting/base transformation are already applied, so this is not raw depth pixels or necessarily unfiltered data |
| `/kinematics/fk_tip_position` | FK endpoint calculated from estimated joint angles and hardware link lengths; records the existing `/tool_endeffector_pose` position with source stamp/frame |

Main columns are `point.x`, `point.y`, `point.z`, `header.frame_id`,
`source_time_ns`, and `bag_receive_time_ns`. Filenames use the existing
topic-name-plus-hash convention; `csv/manifest.json` gives exact topic/file
mappings. Existing `/tool_endeffector_pose`, angle, and TF recording continues.

Each topic records rows **only for messages actually published and received**.
Old values are not copied into failed/missing estimation frames. An optional
topic never published is marked `not_recorded` or `no_messages` in the manifest.
Different topic rates are not forced into shared rows.
Align offline using original source stamps and frames for comparison/training.
`unscaled` is retained to reveal errors that scaling might conceal, not as
independent ground truth. Separately verify inter-camera calibration and the
mounting offset between ID1 and the actual tip.

## AprilTag execution and coordinate frames

The installed `apriltag_ros` is retained, not replaced by Isaac.
In the GUI, start the second AprilTag camera before starting AprilTag.
Existing automatic-start ON/OFF selection remains.
Standalone launch:

```bash
ros2 launch launcher apriltag.launch.py
```

Default inputs are D435i `/tag_camera/tag_camera/color/image_raw` and
`/tag_camera/tag_camera/color/camera_info`.
`image_proc` first rectifies to `/tag_camera/tag_camera/color/image_rect`,
then detection runs while preserving the image stamp and
`tag_camera_color_optical_frame`.
Use `image_topic:=...` and `camera_info_topic:=...` for another camera.
For already rectified D405 images, set `rectify:=false`, supply the existing
D405 image/CameraInfo topics, and match recording settings.
Intrinsics come from CameraInfo; pose scale depends on the physical tag side
length. Repository `launcher/config/apriltag.yaml` specifies
**tag36h11, IDs 0/1, 20 mm**. Size is the outer side of the black border, excluding
white margins; verify it matches the physical printed tag.

| Topic | Pose representation |
|---|---|
| `/apriltag/tag0/pose` | ID0 in the detector's camera optical frame |
| `/apriltag/tag1/pose` | ID1 in the same camera frame |
| `/apriltag/tag1_in_tag0/pose` | ID1 relative to ID0: `inverse(camera_T_ID0) @ camera_T_ID1` |

All are PoseStamped (meters, xyzw quaternion), preserving original image stamps.
Relative pose is calculated **only when both TFs have exactly the same parent
and timestamp**. Occluded/stale tag TFs produce no pose, and `hrm_base` is not
changed. A single detected tag yields only that tag's camera-relative pose.
Raw `/tf` and `/detections` are also retained. YAML content/hash and public
detector/pose-node parameters are included in the session snapshot.

Only the second camera's **CameraInfo, detections, and pose results** are saved.
The default profile saves neither raw nor rectified tag RGB, so tag detection
cannot be rerun later. Public parameters from `/tag_camera/tag_camera` and
content/hash of `launcher/config/realsense_apriltag.yaml` are captured at
recording start. D405 CameraInfo is retained, with only crop color/depth images.

Inter-camera extrinsics are not yet defined. ID1 relative to ID0 is usable,
but D435i camera-relative poses must not be interpreted directly in `hrm_base`.
Both cameras' source header times and bag receive times are preserved separately.
**No automatic synchronization or temporal interpolation is performed.**
Verify camera clock relationships and delays before postprocessing alignment.

With default `auto_export_csv: true`, numeric CSVs are generated automatically
after GUI **Record Stop**. Instead of merging numeric CSVs in real time, a separate
low-priority process reads the closed bag. Setting false skips CSV export but
still runs post-stop bag-integrity checks.
In per-topic CSVs, arrays occupy JSON cells, preserving all four motor/load-cell
channels and all 18 angles. AprilTag exports XYZ, original quaternion, and derived
RPY (radians). Each row has `bag_receive_time_ns` and `source_time_ns`;
headerless messages leave source time blank. TF exports one row per transform,
preserving parent/child and stamp.
The default profile excludes images/depth/clouds/MarkerArray from bags. Crop PNGs
and their index are written by a separate worker during capture. The exporter
still supports older image-containing bags and explicitly selected visualization
profiles: image/cloud CSVs contain only timing/dimensions, while MarkerArray
omission is noted in the manifest.

If the recording node/GUI is closed first, the bag is flushed but CSV processing
may be `pending_or_interrupted`. Convert later **without playing the bag**:

```bash
ros2 run record_pkg export_csv record/<session>
# Existing CSVs or interrupted outputs are not overwritten; re-export elsewhere:
ros2 run record_pkg export_csv record/<session> --output record/<session>/csv_retry
```

Automatic and manual export read all split db3 files through metadata.yaml.
Pass the session or bag directory, not an individual db3 file.
Conversion success and data quality are different: available messages are exported
even when required data are missing. Missing values are documented in the manifest,
not filled with zeros.

### Per-session force-axis alignment in CSV (2026-09-18)

Above the GUI Record button, under **Force axes for CSV (sensor → hrm_base)**,
enable **Add aligned_fx / aligned_fy / aligned_fz** and select axes (initially OFF).
The convention is **output base axis = sign × input sensor axis**, for example:

| GUI setting | Additional value in the same CSV row |
|---|---|
| Base Fx = + sensor Fx | `aligned_fx = +wrench.force.x` |
| Base Fy = − sensor Fy | `aligned_fy = -wrench.force.y` |
| Base Fz = − sensor Fz | `aligned_fz = -wrench.force.z` |

Y/Z exchange example:
`Base Fx=+sensor Fx, Base Fy=-sensor Fz, Base Fz=+sensor Fy`.
Each input axis must appear exactly once; the determinant must be +1 for rotation
between right-handed frames. Duplicate axes and reflection (-1) combinations are
rejected with an explanation. The UI supports axis swaps/sign flips for 90-degree
mounting changes, not arbitrary-angle calibration.

The GUI atomically sends `force_alignment_enabled` and `force_alignment_axes`
(e.g. `['+x', '-y', '-z']`) through `/record/set_parameters_atomically`, requesting
Record only after success. Invalid/obsolete settings are not silently ignored.
GUI settings and corresponding recorder parameters are locked during preparation,
recording, flushing, and CSV export. Changes apply to the next session.
Use only one GUI to initiate collection.

At recording start, settings are fixed in
`session.json → snapshot.force_alignment`, including signed axes, actual
`matrix_base_from_sensor`, target frame `hrm_base`, and unit-preservation notes.
CSV conversion uses **only this session copy**. Later GUI/config changes do not
reinterpret an existing session. Provenance also appears in `csv/manifest.json`
and `session_metadata.csv`.

- Only the CSVs for `/fts_data` and `/fts_data_kalman_filter` gain
  `aligned_fx`, `aligned_fy`, `aligned_fz`, `aligned_frame_id`, and
  `aligned_force_valid`. Original `wrench.force.x/y/z`, torques,
  `header.frame_id`, times, and units remain unchanged.
- Original rosbags, live sensor topics, controller behavior, and motor/load-cell
  protections are unchanged. No aligned topic or live force subscription is
  added; values are calculated in the post-stop CSV.
- When enabled, original NaN/Inf rows remain, but transformed values are
  blank/false. `aligned_force_valid` means numerical computability, not CAN
  connectivity or sensor health. Do not use zeros from a disconnected CAN sensor
  as genuine external-force training labels.
- Units, gain, zero offset, and action/reaction sign are not calibrated.
  Torques are neither rotated nor shifted to another reference point.
  The prefix is deliberately `aligned_`, not `calibrated_`.
- Sensor mounting orientation is assumed fixed within a session. Rotation during
  collection requires a separate time-varying transformation using measured pose.

If OFF, or if an older session lacks the axis snapshot, CSVs remain original-only.
No fixed rotation from older documentation is applied implicitly, and existing
bags/CSVs are not overwritten. Original `/fts_data` already reflects sensor
zero-offset correction and selected LPF/MAF processing; this feature does not
create pre-filter ADC samples. The Kalman topic remains separate.

### Hardware and configuration metadata

At every **Record start**, `session.json.snapshot` stores the following
(schema version 2):

| Field | Content and source |
|---|---|
| `hardware_constants.sources.<node>` | Running controller's read-only `hardware.*` parameters: OP_MODE (8/CSP), motor/joint/segment counts, gearing/encoder, os/l/le/total length, ARC/diameter/WIRE_DISTANCE, angle/tension/motor limits; **values compiled into that binary** |
| `runtime_parameters.nodes.<node>` | Parameter names/types/values queried just after recording start, request/response times, success/missing status; control mode, motor output enable, pan/tilt PD gains, camera settings, etc.; **only values exposed by the node as parameters** |
| `package_configs` | JSON copies of estimation `config.json`/ROI and GUI system-component configuration |
| `reference_files` | Content/path/SHA-256/copy time for those settings, `hw_definition.hpp`, `control_parameters.hpp`, AprilTag and second-camera YAML; disk files at recording start, **not proof of settings active at runtime** |
| `last_observed_filter_setting` | Last `/data_filter_setting` received by the recorder, or `null` if none |

`recording_config.json` preserves session recorder settings, topic selection,
units, and frame notes. Its `notes.hardware` is descriptive, not evidence of
running values; use the source distinctions above.

Default `metadata_nodes` follows current GUI/launch node names. Adjust it when
launching directly as `/ControlNode`, `/segment_estimation_node`, or another
namespace. Queries are asynchronous and finish after a default maximum of
3 seconds (`metadata_timeout_sec`).
Bag capture starts first, but GUI `recording` appears only after parameter
queries complete/time out and bag subscriptions are ready. Stopped nodes or
unavailable parameter services are `unavailable`; no response is `timeout`;
duplicate node names are `ambiguous`.
Missing nonessential metadata alone does not reject capture; the snapshot is
marked `partial`. An immediate Stop marks unfinished queries as `cancelled`.

**OP_MODE is a C++ constant, not a measured drive mode.** It is recorded separately
from `/control_mode` (controller mode) and GUI `op_mode`.
Controller `hardware.*` parameters are read-only and ignore launch/CLI overrides;
change and rebuild the hardware definitions to modify them. **Restart
robot_control and the recorder** after this update to expose the new metadata
(stop safely first if operating). Older controllers report `unavailable`;
reference headers are not used to guess their running values.

The queries are not an atomic multi-node snapshot. Do not change settings during
recording preparation; inspect later changes through `/parameter_events`,
`/control_mode`, and `/data_filter_setting`.
Parameter queries cannot reveal actual driver state or unexposed internal filter
state. In particular, whether declared dynamics/admittance parameters directly
affect internal calculations requires separate verification. Files edited after
node startup may differ from the configuration originally loaded by the node.

Neither real-time numeric CSV merging nor PNG compression/file writing runs in
image callbacks. Crop images pass through a bounded queue (default 16) to a
separate writer. The C++ rosbag engine stores selected numeric messages using a
64 MiB double-buffer cache (up to approximately 128 MiB).
SQLite uses the `resilient` preset without compression. By default, less than
2 GiB free space rejects startup or triggers automatic Stop.
Crop subscriptions are best-effort so recording does not block image publishers;
**lossless reception of every frame is not guaranteed**.
`/tf_static` is transient-local to receive existing transforms.
The installed estimation_pkg FastDDS large-SHM profile is used automatically
without overriding user environment settings. The existing default RMW itself
is unchanged.

Previously, uncompressed RGB+depth alone at
848×480×(3+2)×30 required approximately **61 MB/s, 3.66 GB/min**.
The new defaults compress only crop color/depth; actual size depends on ROI and
image content. Distinguish saved/received counts in `session.json` and image
manifests; neither is synonymous with physical camera FPS.
Unexpected termination/incomplete bags are marked `failed`; required topics
with zero messages result in `INCOMPLETE`.

## Training postprocessing principles

- Defaults save **crop color/depth plus online angles and numeric data**.
  Verify depth counts, calibration, and RGB/depth timing before 3D reprocessing.
  Recognize crop input so that 2D mask/skeleton reprocessing does not crop the
  original ROI a second time.
- Preserve header stamps, frame_id, CameraInfo K/D, and TF as recorded.
  Bag timestamps are receive times and **must not be substituted for exposure
  times**.
- For 3D reprocessing, pass a session's chronological sequence through the same
  causal filter/skeleton/depth/curve-fitting pipeline, then associate sensor/motor
  data with the **source image time**. Validate maximum time differences, sensor
  delays, clock consistency, and interpolation policies; exclude stale samples.
- `fx` corresponds to `/fts_data.wrench.force.x`, distinct from the separate
  Kalman signal. It is already after F/T zero-offset and optional LPF/MAF
  processing, not raw ADC data.
- Select force alignment through the per-session settings above.
  `Fb=[Fsx,-Fsz,Fsy]` is one mounting example, not a default for all experiments.
  Retain raw sensor-frame values. Resolve N/mN units and reaction-force signs
  through actual calibration.
- Snapshot the configuration/ROI and last observed filter setting. Volatile
  filter changes before recorder startup are unknown; `null` means **unconfirmed**.
  Resend the intended filter setting from the GUI after recording starts so it
  is recorded. Initial public ROS parameters are queried separately, but events/
  queries cannot reconstruct unexposed internal configuration.
- Fixed-base averaging and Kalman state depend on warm-up history. Include warm-up
  in training recordings and match online/offline initialization and filter delay.
  Saved TFs can verify the online base origin. A source-file snapshot does not
  guarantee runtime configuration when files were edited after node startup.
  Filter state from unrecorded intervals cannot be reproduced exactly offline.
  Define per-session initialization/warm-up policies separately.
- Per-topic CSV and crop PNG storage are implemented; **training-data
  association/interpolation by image time and offline angle re-estimation** are
  separate follow-up work. Current CSVs retain independent topic sample times
  rather than relabeling latest sensor readings with one image timestamp.

**Bags contain `/motor_command`. Do not play the entire bag in the ROS domain
of a connected robot.** Use a reader for offline training, or replay only
approved sensor topics in an isolated domain.
